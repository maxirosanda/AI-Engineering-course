El problema

De tu computadora a producción

La clase pasada guardamos todo con ChromaDB en una carpeta local. Es excelente para desarrollar y prototipar, pero en producción aparecen otros desafíos.

ChromaDB local

Como un cuaderno en tu escritorio: rápido y simple, pero vive en una sola máquina. Si el contenedor se borra o el disco se llena, el problema es tuyo.

Pinecone en la nube

Como una caja de seguridad en un banco: otro se ocupa del edificio, la seguridad y de que siempre esté abierto. Vos solo guardás y pedís.

DesafíoQué significa
EscalabilidadPasar de miles a millones de vectores sin que la búsqueda se vuelva lenta.
Persistencia distribuidaLos datos no dependen de una sola máquina ni de tu contenedor.
Alta disponibilidadEl servicio sigue respondiendo aunque falle un servidor.
Concepto clave

¿Por qué Pinecone?

Una base de datos vectorial nativa de la nube, pensada para manejar millones (o miles de millones) de vectores con respuestas en milisegundos.

☁️ Serverless

No administrás servidores, nodos ni memoria. Pagás por lo que usás y el almacenamiento crece solo.

⚡ Cómputo y almacenamiento separados

Guardar mucho no hace más lenta la búsqueda: las consultas siguen siendo rápidas sin importar cuántos datos haya.

🔒 Persistencia garantizada

Los datos viven en la infraestructura administrada de Pinecone, no en tu contenedor local.

Serverless no significa "sin servidores": significa que vos no los ves ni los gestionás. Como la luz de tu casa: no tenés una usina, pagás lo que consumís.

En ChromaDB tenías colecciones y metadatos. Acá el índice cumple el rol de la colección, y el namespace es el nivel nuevo.

El índice: dimensión y métrica

Al crear un índice se fijan dos cosas que después no se pueden cambiar:

📏 Dimensión

Cuántos números tiene cada vector. Tiene que coincidir con tu modelo de embeddings: text-embedding-3-small → 1536.

📐 Métrica

Cómo se mide el parecido. Tiene que ser la misma para la que fue entrenado el modelo. Para texto, casi siempre coseno.

MétricaQué miraCuándo usarla
cosineEl ángulo entre los vectoresBúsqueda de textos (la opción por defecto)
dotproductÁngulo y largo de los vectoresSi el modelo lo indica; también búsqueda híbrida
euclideanLa distancia en línea rectaSi el modelo fue entrenado con esa métrica
pc.create_index(
    name="mi-indice-serverless",
    dimension=1536,                 # la de tu modelo de embeddings
    metric="cosine",
    spec=ServerlessSpec(cloud="aws", region="us-east-1"))  # dónde vive

Namespaces: un índice, varias particiones

Un namespace separa los datos dentro del mismo índice. Una búsqueda en un namespace nunca ve los vectores de otro.

🏢 Multi-tenancy

Un namespace por cliente. Los datos de una empresa no se mezclan con los de otra.

cliente-acme
cliente-globex
cliente-initech

🧪 Entornos

Un namespace por etapa. Las pruebas no ensucian los datos reales.

dev
staging
prod
index.upsert(vectors=vectores, namespace="dev-environment")          # guardar en una partición
index.query(vector=consulta, top_k=5, namespace="dev-environment")   # buscar solo ahí

Multi-tenancy = un mismo sistema que atiende a varios clientes ("inquilinos") manteniendo sus datos aislados. El namespace se crea solo la primera vez que guardás algo en él.

El flujo de trabajo

Pinecone no vive solo: el pipeline

1. Ingesta (se hace una vez por documento)

Documentos
→
Chunkingcortar en pedazos
→
Embeddingpasar a vectores
→
upsertsubir a Pinecone

2. Recuperación (se hace en cada pregunta)

Pregunta
→

→

LLMresponde con lo encontrado

Es el mismo RAG de la clase pasada: lo único que cambia es dónde se guardan y se buscan los vectores. El chunking y los embeddings siguen igual.

Errores comunes de arquitectura

ErrorQué pasaCómo evitarlo
Mismatch de dimensionesInsertar un vector de 1536 en un índice creado para 768 da error inmediato.Definí la dimensión en un solo lugar y usala para crear el índice.
Ignorar los namespacesSe mezclan datos de prueba con producción, o de distintos clientes: riesgo de seguridad y resultados confusos.Decidí la estrategia de namespaces antes de cargar datos.
Métrica equivocadaUsar euclidiana con un modelo entrenado para coseno: los resultados empeoran sin dar error.Revisá la documentación del modelo de embeddings.

El tercero es el más peligroso: no avisa. El sistema funciona, pero encuentra peor.

Ejercicio 1: qué tenés que hacer

Objetivo: crear un índice serverless en Pinecone, cargar vectores con metadatos dentro de un namespace y consultar sus estadísticas.

PasoQué hacer
1Inicializar el cliente: pc = Pinecone(api_key=PINECONE_API_KEY).
2Si index_name no está en pc.list_indexes().names(), crearlo con dimension, metric="cosine" y spec=ServerlessSpec(cloud="aws", region="us-east-1"). Esperar a que esté listo antes de seguir.

4Cargar 2 o 3 vectores en el namespace "dev-environment". Cada uno es una tupla (id, valores, metadata), por ejemplo ("vec1", [0.1] * dimension, {"topic": "infraestructura", "priority": "high"}).

Qué necesitás: una cuenta en Pinecone (el plan gratuito alcanza), pip install pinecone y tu clave en la variable de entorno PINECONE_API_KEY.

  • dimension es 1536, la que pasaste al crear el índice.

Ejercicio 1: solución completa y comentada

Código completo · Ejercicio 1🔗 Repositorio en GitHub
# =====================================================================
# EJERCICIO 1: crear un índice serverless, cargar vectores y ver estadísticas
# =====================================================================
# Antes de correrlo (una sola vez), en la terminal:
#     pip install pinecone
# y guardá tu clave en la variable de entorno PINECONE_API_KEY.
# =====================================================================
import os
import asyncio
from dotenv import load_dotenv
from pinecone import Pinecone, ServerlessSpec

load_dotenv()

PINECONE_API_KEY = os.getenv("PINECONE_API_KEY")


# El namespace (partición) donde vamos a guardar los vectores de prueba
NAMESPACE = "dev-environment"


async def setup_vector_infrastructure(index_name: str, dimension: int):
    """Configura Pinecone Serverless y hace una carga inicial."""

    # 1. Inicializar el cliente: es la "conexión" con tu cuenta de Pinecone
    pc = Pinecone(api_key=PINECONE_API_KEY)

    # 2. Crear el índice SOLO si no existe.
    #    list_indexes().names() devuelve los nombres de tus índices.
    #    Así el programa se puede correr muchas veces sin dar error.
    if index_name not in pc.list_indexes().names():
        pc.create_index(
            name=index_name,
            dimension=dimension,   # debe coincidir con el modelo de embeddings
            metric="cosine",       # la métrica habitual para texto
            # ServerlessSpec: en qué nube y región vive el índice
            spec=ServerlessSpec(cloud="aws", region="us-east-1"))

        # Crear un índice tarda unos segundos. Esperamos a que esté listo
        # antes de usarlo; si no, el upsert puede fallar.
        while not pc.describe_index(index_name).status["ready"]:
            await asyncio.sleep(1)

    # 3. Conectarse al índice: "index" es el objeto con el que operamos
    index = pc.Index(index_name)

    # 4. Upsert de prueba dentro de un namespace.
    #    Cada vector es una tupla (id, valores, metadata).
    #    [0.1] * dimension crea una lista de 1536 números: es un vector
    #    "de mentira", solo para probar la infraestructura.
    vectors = [
        ("vec1", [0.1] * dimension, {"topic": "infraestructura", "priority": "high"}),
        ("vec2", [0.2] * dimension, {"topic": "seguridad", "priority": "medium"}),
        ("vec3", [0.3] * dimension, {"topic": "costos", "priority": "low"}),
    ]
    #    upsert = update + insert: si el id existe lo actualiza; si no, lo crea.
    #    Por eso, al correr el programa otra vez, no se duplican.
    index.upsert(vectors=vectors, namespace=NAMESPACE)

    #    Las estadísticas tardan unos segundos en reflejar la carga
    await asyncio.sleep(5)

    # 5. Devolver e imprimir las estadísticas del índice
    stats = index.describe_index_stats()
    print(stats)
    return stats


if __name__ == "__main__":
    # Dimensión 1536: la de text-embedding-3-small de OpenAI
    asyncio.run(setup_vector_infrastructure("mi-indice-serverless", 1536))
Ingesta masiva

En producción no alcanza con "subir archivos"

La velocidad y la precisión de un sistema RAG dependen de cómo se estructuran los datos al momento de cargarlos.

100 documentoscualquier forma funciona
→
1.000.000 de documentosla forma de cargar define todo

📦 Batching

Subir los vectores en lotes en vez de uno por uno.

🏷️ Metadatos

Etiquetar cada vector para poder filtrar al buscar.

A esta escala, los dos dejan de ser "extras" y pasan a ser requisitos de arquitectura.

Batching: subir en lotes

uno por uno

Como hacer un viaje al supermercado por cada producto. Cada vector es una llamada de red aparte: lento, y además chocás con los límites de la API.

en lotes (batch upsert)

Un viaje con el carrito lleno. Menos llamadas de red, y Pinecone procesa cada lote aprovechando su paralelismo interno.

batch_size = 100                              # cuántos vectores van en cada lote

# i NO es un vector: es la POSICIÓN de la lista donde empieza cada lote.
# range(0, total, 100) va saltando de a 100: 0, 100, 200...
for i in range(0, len(vectors), batch_size):

    # lista[desde : hasta] "recorta" un pedazo de la lista (sin incluir "hasta").
    # i + batch_size no suma nada a los vectores: calcula DÓNDE TERMINA el lote.
    lote = vectors[i : i + batch_size]

    index.upsert(vectors=lote, namespace="prod")   # una sola llamada por lote

Ejemplo: una lista de 250 vectores (posiciones 0 a 249)

La animación se repite sola · El recuadro naranja es el recorte vectors[i : i + 100] de cada vuelta

Si el final se pasa del largo de la lista (300 > 250), Python no da error: devuelve lo que haya. Por eso el último lote sale más chico. Resultado: 3 llamadas a Pinecone en vez de 250. Tamaño ideal: entre 100 y 200 vectores por lote.

Metadatos

El filtro rígido: cuando el significado no alcanza

Buscás "factura de Amazon" entre 10 millones de documentos.

solo búsqueda semántica

También trae "facturas de Azure" o "recibos de Walmart": en significado son muy parecidos.

semántica + filtro por metadatos

Primero descarta todo lo que no tenga proveedor = "amazon", y busca por significado solo en lo que queda.

10.000.000todos los vectores
→
Filtro rígidoproveedor = amazon
→
20.000los que cumplen
→
Top 10los más parecidos

Un filtro rígido (hard filter) es de sí o no: el vector cumple la condición o queda afuera. Achica el espacio de búsqueda, baja la latencia y elimina el "ruido".

Para qué se usan los filtros

🏢 Multi-tenancy

Filtrar por user_id u org_id: un usuario nunca ve datos de otro.

📅 Temporalidad

year > 2023: evita traer información obsoleta.

🗂️ Categorización

department == "legal": limita el contexto a un área.

Los filtros se escriben como diccionarios, con operadores que empiezan con $:

OperadorSignificaEjemplo
$eq / $neigual / distinto{"category": {"$eq": "legal"}}
$gt / $gte / $lt / $ltemayor / mayor o igual / menor / menor o igual{"year": {"$gt": 2023}}
$in / $ninestá / no está en una lista{"status": {"$in": ["reviewed", "final"]}}
$and / $orcombinar condiciones{"$or": [{...}, {...}]}

Una búsqueda con filtro

Queremos buscar por similitud solo en documentos de la categoría legal que ya estén revisados o finalizados.

index.query(
    vector=[0.1, 0.2, ...],      # la pregunta, ya convertida en vector
    top_k=10,                    # cuántos resultados queremos
    filter={
        "category": {"$eq": "legal"},                  # categoría igual a legal
        "status":   {"$in": ["reviewed", "final"]},     # estado dentro de la lista
    },
    include_metadata=True,      # que devuelva también las etiquetas
)
  • Varias claves en el mismo diccionario se combinan con "y": tienen que cumplirse todas.
  • El filtro se aplica junto con la búsqueda semántica, no después: por eso también mejora la velocidad.
  • Si guardás el texto original en los metadatos, el resultado ya trae el pedazo listo para el LLM.

El riesgo del "schema drift"

Schema drift = que la forma de los metadatos se vaya "corriendo" con el tiempo, porque cada proceso los guarda a su manera.

sin estándar 
# Proceso A
{"ingest_date": "2025-03-01"}
# Proceso B
{"date_created": "01/03/2025"}

Un filtro por ingest_date ignora en silencio todo lo que cargó el proceso B.

una sola interfaz 
def create_metadata(text, category, author):
    return {
        "category": category,
        "author": author,
        "ingested_at": datetime.now().isoformat(),
        "char_count": len(text),
    }

Todos los procesos arman los metadatos con la misma función.

Como arquitecto, definí una interfaz de metadatos estricta: mismos nombres, mismos tipos, mismo formato de fecha. Podés validarla con Pydantic, como en la clase de LCEL.

# EJERCICIO 2: ingesta en lotes con metadatos y búsqueda filtrada
# =====================================================================
# Continúa el Ejercicio 1: usa el MISMO índice ("mi-indice-serverless").
#
# ¿Qué hace este programa? Tres cosas, en orden:
#   1. INGESTA: toma 5 documentos de texto, los convierte en vectores
#      con OpenAI y los sube a Pinecone EN LOTES (de a 2).
#   2. BÚSQUEDA: hace una pregunta y busca la respuesta SOLO entre los
#      documentos de la categoría "legal" (filtro por metadatos).
#   3. ESTADÍSTICAS: muestra que el índice ahora tiene dos namespaces.
#
# Antes de correrlo (una sola vez), en la terminal:
#     pip install pinecone openai python-dotenv
# y en tu archivo .env (en la misma carpeta que este archivo):
#     PINECONE_API_KEY=...
#     OPENAI_API_KEY=...
# =====================================================================

# ---------------------------------------------------------------------
# IMPORTS: las herramientas que vamos a usar
# ---------------------------------------------------------------------
import os                               # para leer variables de entorno (las claves)
import time                             # para hacer una pausa con time.sleep()
from datetime import datetime           # para guardar la fecha y hora de carga
from typing import List, Dict, Any      # "pistas de tipo": documentan qué recibe y
                                        # devuelve cada función (Python no las exige)
from dotenv import load_dotenv          # lee el archivo .env
from openai import OpenAI               # cliente de OpenAI: genera los embeddings
from pinecone import Pinecone           # cliente de Pinecone: guarda y busca vectores

# Carga las variables del archivo .env como si fueran variables de entorno.
# Después de esta línea, os.getenv("PINECONE_API_KEY") ya devuelve tu clave.
load_dotenv()

# ---------------------------------------------------------------------
# CONSTANTES: valores fijos que usa todo el programa.
# Se escriben en MAYÚSCULAS por convención. Tenerlos en un solo lugar
# evita errores: si hay que cambiar algo, se cambia acá y listo.
# ---------------------------------------------------------------------
INDEX_NAME = "mi-indice-serverless"          # el índice que creó el Ejercicio 1
NAMESPACE = "documentos"                     # otra partición, separada de "dev-environment"
EMBEDDING_MODEL = "text-embedding-3-small"   # genera vectores de 1536 números:
                                             # TIENE que coincidir con la dimensión
                                             # del índice, o Pinecone da error


# ---------------------------------------------------------------------
# EL PIPELINE DE INGESTA
# ---------------------------------------------------------------------
# Una CLASE agrupa datos y funciones que trabajan juntos.
# Acá juntamos todo lo necesario para cargar y buscar documentos:
# la conexión a Pinecone, la conexión a OpenAI y las funciones que las usan.
class IngestionPipeline:

    # __init__ se ejecuta UNA vez, al crear el objeto:
    #     pipeline = IngestionPipeline(index, OpenAI())
    # Guarda las dos conexiones en "self" para que las demás funciones
    # de la clase puedan usarlas (self.index y self.openai).
    def __init__(self, index, openai_client: OpenAI):
        self.index = index              # el índice de Pinecone (donde se guarda)
        self.openai = openai_client     # el cliente de OpenAI (quien vectoriza)

    # -----------------------------------------------------------------
    # embed: texto → vectores
    # -----------------------------------------------------------------
    # Recibe una LISTA de textos y devuelve una LISTA de vectores,
    # en el mismo orden. Ejemplo:
    #     embed(["hola", "chau"])  →  [[0.01, -0.3, ...], [0.2, 0.05, ...]]
    #                                   (1536 números)    (1536 números)
    # Importante: es UNA sola llamada a OpenAI para todo el lote,
    # no una por texto. Menos llamadas = más rápido y más barato.
    def embed(self, texts: List[str]) -> List[List[float]]:
        response = self.openai.embeddings.create(model=EMBEDDING_MODEL, input=texts)

        # response.data es una lista con un resultado por cada texto.
        # De cada resultado nos quedamos solo con .embedding (el vector).
        # Esto es una "list comprehension": una forma corta de escribir
        #     vectores = []
        #     for item in response.data:
        #         vectores.append(item.embedding)
        return [item.embedding for item in response.data]

    # -----------------------------------------------------------------
    # create_metadata: arma las "etiquetas" de cada vector
    # -----------------------------------------------------------------
    # Es la ÚNICA función del programa que arma metadatos. Así todos los
    # vectores tienen las mismas claves, con el mismo formato.
    # Esto evita el "schema drift" (ver la diapositiva del tema):
    # que un proceso guarde "ingested_at" y otro "fecha", y el filtro
    # ignore en silencio a la mitad de los documentos.
    def create_metadata(self, doc_text: str, category: str, author: str) -> Dict[str, Any]:
        return {
            # El texto original. Pinecone guarda NÚMEROS, no texto: si no lo
            # ponemos acá, al buscar recuperaríamos un vector que no podemos
            # leer. Con esto, el resultado ya trae el texto listo para el LLM.
            "text": doc_text,

            # Las etiquetas por las que después vamos a poder FILTRAR
            "category": category,           # "legal", "hr", "finanzas"
            "author": author,               # quién cargó el documento

            # Fecha y hora de carga. isoformat() da un texto estándar:
            #     "2026-11-24T08:30:00.123456"
            # Siempre el mismo formato → se puede comparar y ordenar.
            "ingested_at": datetime.now().isoformat(),

            # Tamaño del texto en caracteres: sirve, por ejemplo, para
            # detectar documentos vacíos o demasiado largos.
            "char_count": len(doc_text),
        }

    # -----------------------------------------------------------------
    # process_and_upsert_batches: carga TODOS los documentos, de a lotes
    # -----------------------------------------------------------------
    # documents:  lista de diccionarios, cada uno con "text", "category" y "author"
    # batch_size: cuántos documentos van en cada lote (100 por defecto)
    # Devuelve:   la cantidad total de vectores subidos
    def process_and_upsert_batches(self, documents: List[Dict], batch_size: int = 100) -> int:
        total = 0   # contador de vectores subidos

        # range(inicio, fin, salto) genera números saltando de a "salto".
        # Con 5 documentos y batch_size=2:  range(0, 5, 2) → 0, 2, 4
        # "i" NO es un documento: es la POSICIÓN donde empieza cada lote.
        for i in range(0, len(documents), batch_size):

            # 1. Recortar el lote: lista[desde : hasta] (sin incluir "hasta")
            #      i = 0 → documents[0:2] → documentos 0 y 1
            #      i = 2 → documents[2:4] → documentos 2 y 3
            #      i = 4 → documents[4:6] → solo el documento 4
            #    En la última vuelta "hasta" (6) se pasa del largo (5), pero
            #    Python NO da error: devuelve lo que haya. Por eso el último
            #    lote sale más chico.
            batch = documents[i : i + batch_size]

            # 2. Sacar los textos del lote y pedir todos sus embeddings juntos.
            #    [doc["text"] for doc in batch] → ["Contrato de...", "Acuerdo de..."]
            #    embeddings queda con un vector por documento, en el mismo orden.
            embeddings = self.embed([doc["text"] for doc in batch])

            # 3. Armar los vectores en el formato que espera Pinecone:
            #    un diccionario con "id", "values" y "metadata".
            #
            #    zip(batch, embeddings) junta cada documento con SU vector:
            #        (doc0, vector0), (doc1, vector1)
            #    enumerate(...) les agrega un número de orden "j" dentro del lote:
            #        j=0 → (doc0, vector0),  j=1 → (doc1, vector1)
            #
            #    El id se calcula con la posición GLOBAL del documento:
            #        i + j + 1  →  en el lote que empieza en i=2:
            #                      j=0 → "doc-3",  j=1 → "doc-4"
            #    (el +1 es para que empiece en "doc-1" y no en "doc-0")
            #
            #    El id es FIJO: si corrés el programa otra vez, "doc-1" sigue
            #    siendo "doc-1", y upsert lo ACTUALIZA en vez de duplicarlo.
            vectors = [
                {
                    "id": f"doc-{i + j + 1}",       # identificador único
                    "values": embedding,            # los 1536 números
                    "metadata": self.create_metadata(
                        doc["text"], doc["category"], doc["author"]),
                }
                for j, (doc, embedding) in enumerate(zip(batch, embeddings))
            ]

            # 4. Subir el lote completo en UNA llamada a Pinecone.
            #    upsert = update + insert: si el id existe, lo actualiza;
            #    si no existe, lo crea.
            #    namespace=NAMESPACE lo guarda en la partición "documentos",
            #    sin tocar los vectores de prueba del Ejercicio 1.
            self.index.upsert(vectors=vectors, namespace=NAMESPACE)
            print(f"Lote subido: {len(vectors)} vectores")
            total += len(vectors)           # igual a: total = total + len(vectors)

        return total

    # -----------------------------------------------------------------
    # search_by_category: busca por significado, pero solo en una categoría
    # -----------------------------------------------------------------
    # question: la pregunta del usuario, en texto
    # category: la categoría donde buscar ("legal", "hr", ...)
    # top_k:    cuántos resultados queremos como MÁXIMO
    def search_by_category(self, question: str, category: str, top_k: int = 5):

        # 1. Pasar la pregunta a vector con el MISMO modelo que los documentos.
        #    Si usáramos otro modelo, los vectores estarían en "mapas"
        #    distintos y la comparación no tendría sentido.
        #    embed() recibe y devuelve LISTAS: le pasamos [question]
        #    (una lista de un elemento) y con [0] tomamos el único vector.
        query_vector = self.embed([question])[0]

        # 2. Buscar en Pinecone los vectores más cercanos a la pregunta.
        return self.index.query(
            vector=query_vector,        # el punto de partida de la búsqueda
            top_k=top_k,                # como máximo, esta cantidad de resultados
            namespace=NAMESPACE,        # buscar SOLO en la partición "documentos"
            # Filtro rígido: "$eq" = "igual a". Los vectores cuya categoría
            # no sea la pedida ni siquiera compiten en la búsqueda.
            filter={"category": {"$eq": category}},
            # Sin esto, Pinecone devuelve solo id y score. Con True,
            # también devuelve los metadatos (incluido el texto original).
            include_metadata=True)


# ---------------------------------------------------------------------
# PROGRAMA PRINCIPAL
# ---------------------------------------------------------------------
def main():
    # Conectarse a Pinecone con la clave del archivo .env
    pc = Pinecone(api_key=os.getenv("PINECONE_API_KEY"))

    # El índice lo creó el Ejercicio 1. Si no existe, no tiene sentido
    # seguir: SystemExit corta el programa con un mensaje claro
    # (mejor que un error confuso más adelante).
    if INDEX_NAME not in pc.list_indexes().names():
        raise SystemExit(f"No existe '{INDEX_NAME}': corré primero el Ejercicio 1.")

    # Conectarse al índice y armar el pipeline.
    # OpenAI() sin argumentos busca solo la variable OPENAI_API_KEY.
    index = pc.Index(INDEX_NAME)
    pipeline = IngestionPipeline(index, OpenAI())

    # Los datos de prueba: 5 documentos (2 de legal, 2 de hr y 1 de finanzas).
    # Cada documento es un diccionario con su texto y sus etiquetas.
    # En un caso real, estos textos saldrían de PDFs o archivos ya cortados
    # en pedazos (chunks).
    docs = [
        {"text": "Contrato de servicios con el proveedor de hosting, vigente por 12 meses.",
         "category": "legal", "author": "User1"},
        {"text": "Acuerdo de confidencialidad (NDA) firmado con la agencia de diseño.",
         "category": "legal", "author": "User1"},
        {"text": "Política de licencias: 15 días de vacaciones y licencia por estudio.",
         "category": "hr", "author": "User2"},
        {"text": "Manual de onboarding para empleados nuevos del área de ventas.",
         "category": "hr", "author": "User2"},
        {"text": "Presupuesto anual 2026 con el detalle de gastos por departamento.",
         "category": "finanzas", "author": "User3"},
    ]

    # ---- PASO 1: INGESTA --------------------------------------------
    # batch_size=2 es MUY chico a propósito, para poder ver los lotes.
    # Con 5 documentos salen 3 lotes: 2 + 2 + 1.
    # En producción se usan lotes de 100 a 200 vectores.
    total = pipeline.process_and_upsert_batches(docs, batch_size=2)
    print(f"Total procesado: {total}")

    # Pinecone tarda unos segundos en dejar "buscables" los vectores nuevos.
    # Si buscáramos enseguida, podríamos recibir 0 resultados.
    time.sleep(10)

    # ---- PASO 2: BÚSQUEDA FILTRADA ----------------------------------
    # Fijate que la pregunta dice "acuerdos de confidencialidad", no "NDA":
    # la búsqueda es por SIGNIFICADO, no por palabras exactas.
    pregunta = "¿Qué acuerdos de confidencialidad tenemos firmados?"
    result = pipeline.search_by_category(pregunta, "legal")

    # result.matches es la lista de resultados, ordenada del más parecido
    # al menos parecido. Cada match trae:
    #     .score    → qué tan parecido es (con coseno: cuanto más alto, mejor)
    #     .id       → el id que le pusimos ("doc-2")
    #     .metadata → el diccionario de create_metadata (con el texto)
    # {match.score:.3f} muestra el número con 3 decimales.
    print(f"\nPregunta: {pregunta}")
    for match in result.matches:
        print(f"  {match.score:.3f} · {match.id} · {match.metadata['text']}")
    # Pedimos top_k=5, pero solo aparecen 2: son los únicos de "legal".

    # ---- PASO 3: ESTADÍSTICAS ---------------------------------------
    # Ahora el índice tiene DOS namespaces: "dev-environment" (3 vectores
    # del Ejercicio 1) y "documentos" (5 vectores de este ejercicio).
    print(index.describe_index_stats())

if __name__ == "__main__":

Resumen de la clase

  • Pinecone Serverless: base vectorial en la nube; no gestionás servidores y pagás por uso.
  • Índice: el contenedor. Fija la dimensión (la de tu modelo) y la métrica (coseno para texto).
  • Namespace: particiones dentro del índice, para separar clientes o entornos.
  • Pipeline: ingesta (chunking → embedding → upsert) y recuperación (embedding → query → LLM).
  • Batching: subir en lotes de 100 a 200 vectores, nunca uno por uno.
  • Metadatos: filtros rígidos ($eq, $in, $gt...) que achican la búsqueda y sacan el ruido.
  • Schema drift: una sola función arma los metadatos, siempre con las mismas claves.

Lo nuevo de la entrega: búsqueda híbrida

🧭 Semántica (Pinecone)

Encuentra por significado. Puede fallar con códigos, siglas o nombres exactos como ERR_4021.

🔤 Léxica (BM25)

Un Ctrl+F mejorado: puntúa los textos según las palabras exactas que comparten con la pregunta.

from langchain_pinecone import PineconeVectorStore
from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever

semantico = vectorstore.as_retriever(search_kwargs={"k": 5})  # Pinecone
lexico = BM25Retriever.from_documents(chunks)                 # palabras exactas
lexico.k = 5

# Combina los dos rankings; weights define cuánto pesa cada uno
hibrido = EnsembleRetriever(retrievers=[lexico, semantico], weights=[0.4, 0.6])
docs = hibrido.invoke("¿Cómo configuro un índice serverless?")[:5]

BM25 necesita pip install rank_bm25. Según tu versión de LangChain, EnsembleRetriever puede importarse desde langchain_classic.retrievers: revisá la documentación de la versión que instales.

Lo nuevo de la entrega: medir si recupera bien

Un golden set es una lista corta de preguntas para las que ya sabés qué documento debería aparecer.

[
  {"pregunta": "¿Cómo se crea un índice serverless?", "documento_id_esperado": "guia-indices.md"},
  {"pregunta": "¿Qué operadores de filtro existen?",  "documento_id_esperado": "metadatos.md"}
]
MétricaQué pregunta respondeCómo se calcula
Recall@5¿Está el documento correcto entre los 5 recuperados?relevantes encontrados ÷ relevantes que existen
Precision@5¿Qué porcentaje de los 5 recuperados es realmente útil?relevantes encontrados ÷ 5

Ejemplo

De 5 recuperados, 2 vienen del documento esperado, que tiene 4 chunks relevantes: Precision@5 = 2/5 = 0,4 · Recall@5 = 2/4 = 0,5.

Ojo al interpretar

Si cada pregunta tiene un solo chunk correcto, la Precision@5 máxima posible es 1/5 = 0,2. No es un mal resultado: es el techo.

Ingesta inteligente: guardá el texto original del chunk dentro de los metadatos. Así la búsqueda ya devuelve el contenido y no hace falta consultar otra base de datos.

errores a evitar
  • Mismatch de dimensiones: subir embeddings de 1536 a un índice creado con 512 o 768.
  • Ignorar el namespace: con varios clientes o tipos de datos, la búsqueda queda ruidosa y lenta.
  • Subestimar el chunking: muy chicos pierden contexto; muy grandes diluyen la precisión. Buscá un punto medio (~500-800 tokens).

Tus claves de API son como contraseñas: no las subas. Dejá el .env en .gitignore y sumá un .env.example con los nombres de las variables, sin los valores.
