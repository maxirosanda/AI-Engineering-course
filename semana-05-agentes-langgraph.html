Qué vamos a ver hoy

Todo apunta a una entrega: un agente de razonamiento cíclico con LangGraph. Para lograrla alcanza con dominar 4 conceptos núcleo:

1. Estado (State)

La "memoria de trabajo" del grafo: TypedDict / MessagesState.

2. Nodos y aristas condicionales

Los pasos y las decisiones: "¿sigo o termino?".

3. Ciclo ReAct

El agente llama a una herramienta, observa el resultado y decide el siguiente paso.

4. Persistencia (checkpointer)

Guardar el estado para que la conversación no se pierda.

El resto es profundización: útil para dominar el tema, pero no hace falta memorizar todo para entregar. Además: dos ejemplos resueltos, dos ejercicios y la Pre-entrega 5.

Los problemas reales no son lineales

Hasta ahora armamos cadenas (LCEL) y sistemas RAG. Pero los sistemas más avanzados no solo "responden": razonan, iteran y corrigen sus propios errores.

Concepto 1

El Estado: la memoria compartida del grafo

🏭 Una línea de ensamblaje

El Estado es el producto que viaja por la cinta. Cada estación (nodo) puede leerlo, modificarlo o agregarle piezas antes de pasarlo a la siguiente.

from typing import Annotated, TypedDict, List
from langchain_core.messages import BaseMessage
from langgraph.graph.message import add_messages

# El esquema de nuestra "memoria de trabajo"
class AgentState(TypedDict):
    # El historial de mensajes: el campo más común.
    # Annotated + un "reducer" definen CÓMO se actualiza este campo
    messages: Annotated[List[BaseMessage], add_messages]
    # Campos propios para la lógica de negocio
    is_escalated: bool
    current_step: str

TypedDict = un diccionario con claves y tipos declarados. Deja a la vista qué datos están "vivos" en la aplicación.

Reducers: cómo se actualiza cada campo

Un nodo no sobrescribe todo el estado: devuelve actualizaciones. Si el estado tiene 10 campos y el nodo devuelve 1, solo cambia ese.

sin reducer 
messages: List[BaseMessage]

Cada vez que un nodo devuelve {"messages": [nuevo]}, la lista anterior desaparece. El agente pierde la conversación.

con reducer 
messages: Annotated[List[BaseMessage],
                    add_messages]

add_messages le dice a LangGraph: "no borres lo anterior, agregá los nuevos al final".

[msg1, msg2]estado actual
+
[msg3]lo que devuelve el nodo
→
[msg1, msg2, msg3]estado nuevo

Reducer = la regla que combina el valor viejo con el nuevo. Atajo: MessagesState ya trae el campo messages con add_messages incluido.

Concepto 2

Nodos: las unidades de trabajo

Un nodo es simplemente una función de Python (síncrona o async): recibe el estado actual y devuelve una actualización.

async def call_model(state: AgentState):
    # 1. Leemos información del estado
    messages = state["messages"]

    # 2. Hacemos el trabajo (ej.: llamar al LLM)
    response = await model.ainvoke(messages)

    # 3. Devolvemos SOLO lo que cambia; LangGraph lo fusiona con el estado
    return {"messages": [response]}

🧠 Un LLM

Lee el historial y decide qué hacer.

🔧 Una herramienta

Consulta una base de datos o una API.

⚙️ Lógica de negocio

Valida un JSON, formatea un texto, cambia una bandera.

Principio de diseño: nodos chicos y con una sola responsabilidad. Un nodo es una unidad de software que se puede probar, no una "caja negra mágica".

Aristas: el control del flujo

Si los nodos son las estaciones, las aristas (edges) son las reglas que dicen adónde va el producto al salir de cada una.

Arista directa

"Cuando termines en A, andá siempre a B."

workflow.add_edge(
    "limpiar_texto",
    "analizar_sentimiento")
la clave de los agentes

Arista condicional

El flujo se bifurca según lo que diga una función de enrutamiento.

def route_after_analysis(state: AgentState):
    if state["sentiment"] == "negative":   # sentimiento negativo: escalamos
        return "human_support"
    return "end"                           # si no, terminamos

workflow.add_conditional_edges(
    "analizar_sentimiento",               # desde qué nodo sale
    route_after_analysis,                 # la función que decide
    {"human_support": "nodo_humano", "end": END})  # respuesta -> destino

Una arista condicional puede devolver el flujo a un nodo anterior: así nace un ciclo. Por ejemplo, un "Validador" que manda la respuesta de vuelta al "Escritor" para corregirla.

Compilar el grafo

Con los nodos y las aristas definidos, el grafo se compila (app = workflow.compile()). Al compilar, LangGraph valida que:

Hay una entrada

Un punto de partida: START.

Hay una salida

Todos los caminos pueden llegar a END.

Nada suelto

No hay nodos aislados.

Ejemplo resuelto 1

Un grafo de soporte con ciclo y escalado

Un grafo mínimo que busca una solución, reintenta si no la encuentra y escala a un humano tras 3 intentos. Corre sin API keys: la búsqueda está simulada.

START
→
searchbusca (simulado)
→
route¿qué hago ahora?
→
"end" → ENDsi está resuelto
"escalate" → human → ENDsi ya van 3 intentos
"retry" → vuelve a searchsi no: este es el CICLO
Campo del estadoPara qué sirve
queryLa consulta del usuario
attemptsCuántas veces se buscó (para cortar el ciclo)
solvedSi ya se encontró una solución
escalatedSi el caso pasó a un humano

Cuando dibujes un grafo: nodos = cajas, add_conditional_edges = la bifurcación, y "retry" = la flecha que vuelve hacia atrás.

Ejemplo 1: código completo y comentado

Código completo · copiá, pegá y corré · sin API keys 
# =====================================================================
# EJEMPLO 1: grafo de soporte con ciclo de reintento y escalado
# =====================================================================
# Antes de correrlo (una sola vez), en la terminal:
#     pip install langgraph
# =====================================================================
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

# 1. El Estado: la "memoria de trabajo" que viaja por el grafo
class SupportState(TypedDict):
    query: str        # la consulta del usuario
    attempts: int     # cuántas veces buscamos
    solved: bool      # ¿ya hay solución?
    escalated: bool   # ¿pasó a un humano?

# 2. Nodo: busca en la base de conocimiento (simulado)
def search_knowledge(state: SupportState) -> dict:
    intento = state["attempts"] + 1
    # Simulamos que recién encuentra la solución en el 2.º intento
    encontrado = intento >= 2
    print(f"[search] intento {intento} -> {'resuelto' if encontrado else 'sin resultado'}")
    # Devuelve SOLO los campos que cambian, no el estado completo
    return {"attempts": intento, "solved": encontrado}

# 3. Nodo: escala el caso a un humano
def human_support(state: SupportState) -> dict:
    print("[human] caso escalado a soporte humano")
    return {"escalated": True}

# 4. Función de enrutamiento: mira el estado y decide el camino.
#    Devuelve una "etiqueta"; el grafo la traduce a un nodo destino.
def route(state: SupportState) -> str:
    if state["solved"]:
        return "end"
    if state["attempts"] >= 3:    # freno: corta el ciclo para no quedar infinito
        return "escalate"
    return "retry"                # vuelve a 'search' -> esto crea el CICLO

# 5. Construcción del grafo
workflow = StateGraph(SupportState)          # un grafo que usa este estado
workflow.add_node("search", search_knowledge)  # nombre del nodo + su función
workflow.add_node("human", human_support)

workflow.add_edge(START, "search")            # el grafo arranca en 'search'
workflow.add_conditional_edges(
    "search",                                # al salir de 'search'...
    route,                                   # ...esta función decide...
    {"end": END, "escalate": "human", "retry": "search"},  # ...etiqueta -> destino
)
workflow.add_edge("human", END)               # después del humano, termina

app = workflow.compile()                     # valida y deja el grafo listo

# 6. Ejecución: le pasamos el estado inicial
final = app.invoke(
    {"query": "No puedo iniciar sesión", "attempts": 0, "solved": False, "escalated": False}
)
print(final)

Ejemplo 1: qué deberías ver

[search] intento 1 -> sin resultado
[search] intento 2 -> resuelto
{'query': 'No puedo iniciar sesión', 'attempts': 2, 'solved': True, 'escalated': False}
  • El estado arranca con attempts=0. Cada nodo devuelve solo lo que cambia; LangGraph lo fusiona.
  • START → search: el primer intento no encuentra solución (solved=False).
  • route lee el estado: no está resuelto y no llegó a 3 intentos → "retry" → vuelve a search. Ese retorno es el ciclo que una cadena lineal no puede hacer.
  • En el segundo intento solved=True: route devuelve "end" y el grafo termina sin escalar.

Probá el otro camino: cambiá encontrado = intento >= 2 por encontrado = False. Tras 3 intentos, la ruta pasa a "escalate" → nodo human → escalated=True → END.

Bucle de reflexión: escritor ↔ crítico

El otro ciclo clásico de los agentes: un nodo escribe, otro evalúa, y se repite hasta alcanzar la calidad buscada.

START
→
escritormejora el borrador
→
críticopunto de decisión
→
"aprobado" → ENDscore ≥ 8
"rendirse" → END4 revisiones: freno de seguridad
"revisar" → vuelve a escritorel CICLO de reflexión
[escritor] revisión 1 -> score 3

Borrador sobre 'onboarding de usuarios' (calidad 9/10)

Ejemplo 1: reintento

Se repite porque algo falló.

Ejemplo 2: mejora iterativa

Se repite para mejorar: el sistema se autocritica. Es la base de los agentes "reflexivos".

Ejemplo 2: código completo y comentado

Código completo · copiá, pegá y corré · sin API keys 
# =====================================================================
# EJEMPLO 2: bucle de reflexión (escritor <-> crítico)
# =====================================================================
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

# 1. Estado: el borrador, su puntaje y cuántas veces lo revisamos
class WriteState(TypedDict):
    tema: str
    borrador: str
    score: int
    revisiones: int

# 2. Nodo escritor: genera o mejora el borrador.
#    Simulado: cada vuelta suma 3 puntos de calidad.
#    (En un agente real, acá iría la llamada al LLM.)
def escribir(state: WriteState) -> dict:
    nuevo_score = state["score"] + 3
    print(f"[escritor] revisión {state['revisiones'] + 1} -> score {nuevo_score}")
    return {
        "borrador": f"Borrador sobre '{state['tema']}' (calidad {nuevo_score}/10)",
        "score": nuevo_score,
        "revisiones": state["revisiones"] + 1,
    }

# 3. Nodo crítico: no modifica el estado (devuelve {}).
#    Es solo el punto donde la arista condicional evalúa.
def criticar(state: WriteState) -> dict:
    return {}

# 4. Enrutamiento: ¿aprobamos, nos rendimos o seguimos revisando?
def route(state: WriteState) -> str:
    if state["score"] >= 8:
        return "aprobado"
    if state["revisiones"] >= 4:   # tope: sin esto, un borrador que nunca
        return "rendirse"           # llega a 8 generaría un loop infinito
    return "revisar"                # vuelve al escritor -> CICLO de reflexión

# 5. Construcción del grafo
g = StateGraph(WriteState)
g.add_node("escritor", escribir)
g.add_node("critico", criticar)

g.add_edge(START, "escritor")
g.add_edge("escritor", "critico")     # siempre: escritor -> crítico
g.add_conditional_edges(
    "critico",
    route,
    {"aprobado": END, "rendirse": END, "revisar": "escritor"},
)

app = g.compile()

# 6. Ejecución
final = app.invoke({"tema": "onboarding de usuarios", "borrador": "", "score": 0, "revisiones": 0})
print(f"Final tras {final['revisiones']} revisiones | score {final['score']}")
print(final["borrador"])
Tool calling

Tool calling: darle "manos" al modelo

Un LLM solo es como un cerebro brillante en una habitación sin ventanas: razona, pero no puede interactuar con el mundo.

LLM"quiero ejecutar multiply(5, 2)"
→
Tu aplicaciónvalida y ejecuta el código real
→
Resultado: 10vuelve al LLM
lo que NO pasa

El modelo no ejecuta código Python por su cuenta.

lo que sí pasa

El modelo genera un pedido estructurado (JSON): qué función quiere y con qué parámetros. Tu app lo intercepta y lo ejecuta.

Como en un restaurante: el cliente (LLM) pide un plato del menú; la cocina (tu código) es la que cocina.

El "contrato" de una herramienta

PilarQué es
NombreIdentificador único, como get_stock_price.
DescripciónExplica para qué sirve. El LLM decide si usarla leyendo esto.
Esquema de entradaQué parámetros recibe: tipos y cuáles son obligatorios.
Esquema de salidaQué devuelve.
from pydantic import BaseModel, Field
from langchain_core.tools import tool

class CalculatorInput(BaseModel):            # esquema de entrada, validado por Pydantic
    a: int = Field(description="Primer número")
    b: int = Field(description="Segundo número")

@tool(args_schema=CalculatorInput)          # convierte la función en herramienta
def multiply(a: int, b: int) -> int:         # el nombre de la función = nombre de la tool
    """Multiplica dos números enteros."""     # el docstring = la descripción
    return a * b

No se puede confiar en que el LLM mande siempre datos correctos: Pydantic valida los tipos antes de que el código toque tu infraestructura.

El ciclo de ejecución, paso a paso

PasoQué pasa
1 · RazonamientoEl LLM recibe el prompt y las definiciones de las herramientas. Decide que necesita multiply.
2 · Tool callResponde con un objeto especial: tool_calls: [{name: 'multiply', args: {a: 5, b: 2}}].
3 · Ejecución (local)Tu servidor detecta el pedido, valida los argumentos con Pydantic y ejecuta multiply(5, 2).
4 · ObservaciónEl resultado (10) vuelve al LLM en un mensaje nuevo, con el rol tool.
5 · Respuesta finalEl LLM procesa el 10 y le responde al usuario: "El resultado es 10".

→
tu código ejecuta
→

Para que el modelo conozca las herramientas, se las "atás" con model.bind_tools(tools).

Errores comunes y seguridad

ErrorQué pasaQué hacer
Confundir invocación con ejecuciónEl LLM pide; quien ejecuta es tu código. Lo que pida se va a ejecutar con tus permisos.Herramientas con permisos mínimos (least privilege). Nunca ejecutar SQL crudo generado por el LLM sin validarlo.

Si el agente no usa la herramienta que esperabas, el problema casi siempre está en el docstring, no en la lógica del grafo.

Ejercicio 1: qué tenés que hacer

Objetivo: definir una herramienta que un agente pueda usar, con un contrato de entrada validado por Pydantic y una descripción clara para que el LLM sepa cuándo llamarla.

PasoQué hacer
1Definir SearchInput(BaseModel) con query: str y limit: int = 3. Usar Field(..., description="...") en los dos, y en limit agregar ge=1, le=10.
2Decorar la función con @tool(args_schema=SearchInput) y dejarla asíncrona (async def).
3Reescribir el docstring: qué busca, cuándo conviene usarla y qué devuelve. Es la instrucción que lee el LLM.
4Adentro, llamar a await db.similarity_search(query, k=limit) dentro de un try. Si falla, devolver un mensaje de error en lugar de cortar la ejecución.

Ejercicio 1: solución completa y comentada

Código completo · copiá, pegá y corré · sin API keys 
# =====================================================================
# EJERCICIO 1: una herramienta con contrato validado por Pydantic
# =====================================================================
# Antes de correrlo (una sola vez), en la terminal:
#     pip install langchain-core pydantic
# =====================================================================
import asyncio
from typing import List
from pydantic import BaseModel, Field, ValidationError
from langchain_core.tools import tool


# ---------------------------------------------------------------------
# PASO 1: el esquema de entrada (el "contrato" de los parámetros)
# ---------------------------------------------------------------------
class SearchInput(BaseModel):
    # "..." significa: campo obligatorio, sin valor por defecto.
    # La description la lee el LLM para saber qué poner en cada parámetro.
    query: str = Field(
        ..., description="Texto a buscar en la base de conocimiento, en lenguaje natural")
    # Valor por defecto 3. ge=1 y le=10: tiene que estar entre 1 y 10.
    # Así el LLM no puede pedir 5.000 resultados por error.
    limit: int = Field(
        3, ge=1, le=10, description="Cantidad máxima de resultados a devolver (entre 1 y 10)")


# Simulación de una base de datos vectorial (viene dada en el ejercicio)
class MockVectorDB:
    async def similarity_search(self, query: str, k: int):
        return [f"Resultado para {query}"]

db = MockVectorDB()


# ---------------------------------------------------------------------
# PASOS 2, 3 y 4: la herramienta
# ---------------------------------------------------------------------
# @tool convierte la función en una herramienta de LangChain.
# args_schema asocia el esquema: los argumentos se validan ANTES de ejecutar.
@tool(args_schema=SearchInput)
async def search_knowledge_base(query: str, limit: int = 3) -> List[str] | str:
    """Busca información en la base de conocimiento interna de la empresa
    (políticas, manuales y documentación).

    Usala cuando el usuario pregunte por procedimientos, normas o datos
    internos que no sean de conocimiento general.

    Devuelve una lista con los fragmentos de texto más relevantes.
    """
    # El docstring de arriba es la "instrucción" que lee el LLM:
    # qué busca, cuándo usarla y qué devuelve.
    try:
        # async + await: la búsqueda no bloquea el event loop
        return await db.similarity_search(query, k=limit)
    except Exception as e:
        # No dejamos escapar la excepción: devolvemos el error como texto.
        # Así el LLM puede explicarle al usuario qué pasó o probar otra cosa.
        return f"Error al buscar en la base de conocimiento: {e}"


# ---------------------------------------------------------------------
# PRUEBA: no hace falta ningún LLM
# ---------------------------------------------------------------------
if __name__ == "__main__":
    # El "contrato" tal como lo ve el modelo: nombre y argumentos
    print(search_knowledge_base.name, search_knowledge_base.args)

    # Ejecutamos la herramienta a mano, como lo haría el agente
    print(asyncio.run(search_knowledge_base.ainvoke(
        {"query": "políticas de vacaciones", "limit": 2})))

    # limit=50 rompe el contrato (máximo 10): Pydantic lo rechaza
    try:
        asyncio.run(search_knowledge_base.ainvoke({"query": "vacaciones", "limit": 50}))
    except ValidationError as e:
        print("Error de validación:", e.errors()[0]["msg"])
Concepto 3

El ciclo ReAct: razonar + actuar

ReAct (Reasoning + Acting) es el patrón estándar de los agentes autónomos. A diferencia de una cadena, es cíclico.

Pensar¿qué necesito?
→
Actuarelegir herramienta y parámetros
→
Observarleer el resultado
↺
Respondercuando ya no hacen falta herramientas

En LangGraph se arma con dos nodos y una arista condicional:

La animación se repite sola · El punto es la ejecución; a la derecha, cómo crece el historial

El LLM puede usar tres herramientas distintas antes de responder. Cada vuelta suma mensajes al historial (el pedido y la observación). ToolNode y tools_condition ya vienen hechos en langgraph.prebuilt.

Concepto 4

Checkpoints: la "caja negra" del agente

Un agente puede fallar a mitad de una ejecución de 10 pasos (un error de red, un timeout). Sin persistencia, se pierde todo el razonamiento, los resultados parciales y la plata gastada en tokens.

📸 Checkpointer

Guarda una "foto" del estado después de cada nodo, como el guardado automático de un videojuego.

🧵 thread_id

El identificador de la conversación. Mismo thread_id = se carga el último estado guardado y se sigue desde ahí.

memory = MemorySaver()                          # guarda en memoria (para probar)
app = workflow.compile(checkpointer=memory)

config = {"configurable": {"thread_id": "sesion-1"}}
await app.ainvoke({"messages": [...]}, config)    # mismo config = misma conversación
Qué permitePara qué
ReanudarSi el proceso se corta, se retoma con el mismo thread_id.

Ejercicio 2: solución completa y comentada

Código completo · necesita OPENAI_API_KEY 
# =====================================================================
# EJERCICIO 2: agente ReAct con memoria (checkpointer)
# =====================================================================
# Antes de correrlo (una sola vez), en la terminal:
#     pip install langgraph langchain-openai
# y guardá tu clave en la variable de entorno OPENAI_API_KEY.
# =====================================================================
import asyncio
from typing import Annotated, TypedDict
from langchain_openai import ChatOpenAI
from langchain_core.messages import BaseMessage, HumanMessage
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition
from langgraph.checkpoint.memory import MemorySaver


# 1. El Estado del agente.
#    add_messages hace que el historial sea ACUMULATIVO: cada nodo agrega
#    mensajes en vez de pisar los anteriores.
class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]


# 2. Herramientas. El docstring es lo que lee el LLM para decidir usarla.
def get_weather(location: str):
    """Consulta el clima actual."""
    return "Soleado, 22°C"     # simulado: siempre devuelve lo mismo

tools = [get_weather]

#    ToolNode: un nodo ya hecho que ejecuta la herramienta que pidió el LLM
#    y devuelve el resultado como un mensaje con rol "tool".
tool_node = ToolNode(tools)

# 3. El modelo. bind_tools le "presenta" las herramientas: a partir de acá
#    el LLM puede responder con texto o con un pedido de herramienta.
model = ChatOpenAI(model="gpt-4o-mini", temperature=0).bind_tools(tools)


# 4. Nodo del agente: le manda TODO el historial al modelo
async def call_model(state: AgentState):
    response = await model.ainvoke(state["messages"])
    # Devolvemos solo el mensaje nuevo; add_messages lo suma al historial
    return {"messages": [response]}


# 5. Construcción del grafo: el ciclo ReAct
workflow = StateGraph(AgentState)
workflow.add_node("agent", call_model)   # piensa
workflow.add_node("tools", tool_node)    # actúa

workflow.add_edge(START, "agent")

#    tools_condition mira el último mensaje del agente:
#      - si pidió una herramienta -> va al nodo "tools"
#      - si no                    -> va a END (el grafo termina)
workflow.add_conditional_edges("agent", tools_condition)

#    Después de ejecutar la herramienta, SIEMPRE vuelve al agente para que
#    observe el resultado. Esta arista cierra el ciclo.
workflow.add_edge("tools", "agent")

# 6. Persistencia: MemorySaver guarda una "foto" del estado tras cada nodo.
#    (Vive en memoria: se pierde al cerrar el programa. Sirve para probar.)
memory = MemorySaver()
app = workflow.compile(checkpointer=memory)


async def main():
    # thread_id identifica la conversación. Mismo id = misma memoria.
    # recursion_limit: techo de pasos, para que un ciclo no gaste de más.
    thread_config = {"configurable": {"thread_id": "sesion-1"}, "recursion_limit": 10}

    # Paso 1: una pregunta completa
    r1 = await app.ainvoke(
        {"messages": [HumanMessage(content="¿Qué tiempo hace en Madrid?")]},
        thread_config)
    print("--- Paso 1 ---")
    print(r1["messages"][-1].content)   # [-1] = el último mensaje (la respuesta)

    # Paso 2: una pregunta que solo se entiende con el contexto anterior.
    # Mandamos SOLO el mensaje nuevo: el checkpointer carga el resto.
    r2 = await app.ainvoke(
        {"messages": [HumanMessage(content="¿Y en Londres?")]},
        thread_config)
    print("\n--- Paso 2 ---")
    print(r2["messages"][-1].content)

    # Para comprobar la memoria: usá otro thread_id en el paso 2
    # (ej.: "sesion-2"). El agente ya no va a saber de qué le hablás.


if __name__ == "__main__":
    asyncio.run(main())

Resumen de la clase

  • LangGraph extiende LangChain con grafos que admiten ciclos y un estado compartido.
  • Estado: la única fuente de verdad, tipada, que viaja por el grafo. Los nodos devuelven actualizaciones; los reducers (add_messages) definen cómo se combinan.
  • Nodos: funciones chicas que transforman el estado. Aristas: las reglas de navegación; las condicionales permiten bifurcar y volver atrás.
  • Todo ciclo necesita un freno: un contador en el estado o un recursion_limit.
  • Tool calling: el LLM pide, tu código ejecuta. Contrato con Pydantic, docstring claro, errores devueltos como texto.
  • ReAct: pensar → actuar → observar, con ToolNode y tools_condition.
  • Checkpointer + thread_id: el agente recuerda la conversación y puede reanudarse.

Pre-entrega 5

Agente de razonamiento cíclico con memoria persistente

Para aprobar, tu agente tiene que cumplir cuatro criterios:

🤖 Autonomía

Decide por sí mismo cuándo llamar a una herramienta, según el pedido del usuario. Sin rutas manuales if/else.

🔁 Ciclo de retorno

Si una herramienta devuelve un error o información incompleta, hace un segundo intento o pide aclaraciones.

🧵 Resiliencia de estado

Con un thread_id, recuerda las interacciones previas de la misma sesión.

✨ Código limpio

Python 3.12, type hints y gestión asíncrona con asyncio.

Usuario: "¿Cuántos pedidos tuvo el cliente 102 y cuál fue el total?"
→ El agente decide usar la herramienta: buscar_pedidos(cliente_id=102)
→ La herramienta devuelve: { "pedidos": 3, "total": 14500 }
→ El agente razona: ya tiene los datos → responde.
Respuesta: "El cliente 102 tuvo 3 pedidos por un total de $14.500."
