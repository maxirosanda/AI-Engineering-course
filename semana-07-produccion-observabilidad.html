El problema

El "éxito silencioso"

En producción, "funciona en mi computadora" es una frase peligrosa. Los sistemas con LLM son probabilísticos y opacos: pueden fallar sin lanzar ningún error.

software tradicional

Un error es binario: el código rompe o funciona. Si rompe, hay una excepción y un log.

ingeniería de IA

El usuario recibe una respuesta bien formateada. La API devuelve 200 OK. Pero el agente ignoró las herramientas, usó un contexto irrelevante o alucinó una cifra crítica.

Sin observabilidad, estás volando a ciegas.

Observabilidad no es solo "loggear" texto: es poder reconstruir lo que pasó adentro del sistema a partir de lo que deja afuera: trazas, métricas y evaluaciones.

Conceptos clave

Trazas, spans y runs

PalabraQué significa
trace (traza)El viaje completo de un pedido: desde que el usuario manda el mensaje hasta la respuesta final.
span (lapso)Una unidad de trabajo dentro de la traza: una búsqueda vectorial, una llamada al LLM, la ejecución de una herramienta.
run (ejecución)En LangSmith: la ejecución de un Runnable de LangChain.

Los spans son jerárquicos: una traza es un árbol de spans.

traza: "¿Cuánto tarda un envío al interior?"                    4,2 s
 ├── span: retriever (búsqueda en Pinecone)                     0,3 s
 ├── span: agente
 │    ├── span: llamada al LLM (decide usar una herramienta)    1,4 s
 │    ├── span: tool consultar_envios                           0,6 s
 │    └── span: llamada al LLM (redacta la respuesta)           1,9 s
 └── respuesta final

Como el seguimiento de un paquete: la traza es el viaje entero; cada span, una escala (depósito, aduana, reparto), con su hora de entrada y de salida.

¿Para qué separar en spans?

Tu sistema tarda 10 segundos en responder. ¿Dónde se fue el tiempo?

solo un log de inicio y de fin 
10:00:00  inicio
10:00:10  fin

No sabés si fue la latencia del modelo, una búsqueda lenta en Pinecone o un bucle en tu grafo.

con spans 
retriever      0,4 s
LLM            1,6 s
tool buscar    7,5 s   ← acá
LLM            0,5 s

El cuello de botella se ve al instante.

PiezaQué te dice
TrazasLa historia de lo que pasó.
SpansDónde falló o se puso lento.
EvalsSi el resultado es confiable.
Herramientas

Arize Phoenix vs. LangSmith

🐦‍🔥 Arize Phoenix

Abierto y local-first. Código abierto, basado en el estándar OpenInference (una extensión de OpenTelemetry para IA).

  • Agnóstico del framework: LangChain, LlamaIndex o el SDK puro de OpenAI.
  • Privacidad: corre en tu máquina (Docker o notebook); los datos no salen de tu infraestructura.
  • Foco: análisis de embeddings, detección de drift y evaluaciones de RAG.

🦜 LangSmith

La experiencia integrada de LangChain. La opción natural si tu stack es LCEL o LangGraph.

  • Plug-and-play: con un par de variables de entorno, cada paso se registra solo.
  • Debugging: editar y re-ejecutar prompts desde la interfaz, sin reiniciar el servidor.
  • Datasets: armar conjuntos de prueba a partir de trazas reales, para pruebas de regresión.
Si...Elegí

todo tu sistema es LangChain / LangGraph y querés lo más rápido de configurarLangSmith

Drift (deriva) = cuando los datos que recibe el sistema en producción empiezan a parecerse cada vez menos a los que tenía cuando lo probaste.

Latencia y costos: mirar los percentiles

Un error de principiante es mirar solo la latencia promedio. En producción importan los percentiles.

MétricaQué significa
p50La mediana: la mitad de las respuestas tarda menos que esto.
p95El 95% tarda menos que esto. O sea: lo que sufre el 5% de usuarios con peor experiencia.
p99Igual, pero para el 1% más lento.
el promedio engaña

Promedio: 3 segundos. p95: 45 segundos. Hay un problema grave de experiencia de usuario que el promedio esconde: 1 de cada 20 personas espera casi un minuto.

💰 Costos

Phoenix y LangSmith calculan el costo solos, a partir de los tokens de entrada y de salida que informa cada respuesta del modelo. Así ves qué agente o qué usuario se come el presupuesto.

Las dos métricas que pide la entrega salen de acá: costo por ejecución y latencia p95.

Evaluadores: detectar alucinaciones

El monitoreo tradicional usa chequeos de sí o no. En IA se usan evaluadores (LLM-as-a-judge): otro modelo que le pone nota a la respuesta.

La tríada de RAGLa pregunta que responde
Faithfulness (fidelidad)¿La respuesta sale solo del contexto recuperado? Si el LLM usa su conocimiento propio, cuenta como alucinación, aunque el dato sea cierto: rompe el control del sistema.
Answer relevance¿La respuesta contesta lo que preguntó el usuario?
Context precision¿Los documentos recuperados eran realmente útiles para responder?
error típico: optimizar el componente equivocado

La respuesta es mala y te ponés a cambiar el prompt. Pero la traza muestra que el problema estaba antes: el retriever no trajo la información de Pinecone. Sin mirar el span de recuperación, estarías arreglando lo que no está roto.

Redis, polling y dos errores a evitar

🧱 ¿Por qué Redis?

No es solo un caché. Tiene estructuras como Lists (colas simples) y Streams (eventos), y trabaja en memoria: coordina miles de tareas casi sin latencia.

🔁 Polling (sondeo)

El cliente pregunta cada tanto a /status/{job_id} si la tarea terminó. Simple, robusto y más fácil de desplegar que WebSockets.

await redis.rpush("tasks_queue", job_id)            # la API agrega al FINAL de la cola
_, job_id = await redis.blpop("tasks_queue")       # el worker saca del PRINCIPIO (y espera si está vacía)
ErrorQué pasa
Ejecutar la IA directamente en el endpointBloqueás el hilo de ejecución, y la API deja de responderles a los demás usuarios.
No guardar el estado inicialSi encolás antes de escribir el estado pending, un cliente rápido puede consultar y recibir un 404: el registro todavía no existe. Siempre registrá el estado antes de encolar.

Ejercicio 1: solución completa y comentada

Código completo · necesita Redis en localhost:6379 
# =====================================================================
# EJERCICIO 1: API + cola en Redis + worker (patrón de polling)
# =====================================================================
# Antes de correrlo:
#     docker run -d -p 6379:6379 redis
#     pip install fastapi uvicorn redis
#     uvicorn main:app --reload      (si el archivo se llama main.py)
# =====================================================================
import asyncio
import uuid     # genera identificadores únicos
import json     # Redis guarda texto: convertimos los dict a JSON y de vuelta
from fastapi import FastAPI, HTTPException
from redis import asyncio as aioredis   # el cliente ASÍNCRONO de Redis
from pydantic import BaseModel

# Configuración de Redis
REDIS_URL = "redis://localhost:6379"
QUEUE_NAME = "tasks_queue"     # la lista que funciona como cola
STATUS_PREFIX = "status:"      # cada tarea se guarda como "status:<job_id>"

app = FastAPI()
# decode_responses=True: Redis devuelve texto (str) en vez de bytes
redis_client = aioredis.from_url(REDIS_URL, decode_responses=True)

class TaskRequest(BaseModel):
    query: str


# ---------------------------------------------------------------------
# EL RECEPCIONISTA: recibe, registra, encola y responde al instante
# ---------------------------------------------------------------------
@app.post("/process")
async def create_task(request: TaskRequest):
    # El "ticket" que le damos al cliente
    job_id = str(uuid.uuid4())

    # 1. PRIMERO registramos el estado inicial...
    job = {"status": "pending", "query": request.query, "result": None}
    await redis_client.set(f"{STATUS_PREFIX}{job_id}", json.dumps(job))

    # 2. ...y RECIÉN DESPUÉS encolamos. Si fuera al revés, un worker rápido
    #    podría tomar la tarea antes de que exista su registro, y el cliente
    #    recibiría un 404 al consultar.
    await redis_client.rpush(QUEUE_NAME, job_id)   # rpush = agrega al final

    # 3. Respondemos ya: NO esperamos a que la tarea termine
    return {"job_id": job_id, "status": "pending"}


# ---------------------------------------------------------------------
# POLLING: el cliente pregunta cómo va su tarea
# ---------------------------------------------------------------------
@app.get("/status/{job_id}")
async def get_status(job_id: str):
    data = await redis_client.get(f"{STATUS_PREFIX}{job_id}")
    if data is None:
        # Ese ticket no existe
        raise HTTPException(status_code=404, detail="Job no encontrado")
    return json.loads(data)


# ---------------------------------------------------------------------
# EL ESPECIALISTA: saca tareas de la cola y las procesa, para siempre
# ---------------------------------------------------------------------
async def task_worker():
    while True:
        # blpop = saca del principio de la cola. Si está vacía, ESPERA
        # (timeout=0: sin límite) sin gastar CPU ni bloquear el event loop.
        # Devuelve (nombre_de_la_cola, valor).
        _, job_id = await redis_client.blpop(QUEUE_NAME, timeout=0)
        key = f"{STATUS_PREFIX}{job_id}"
        job = json.loads(await redis_client.get(key))

        try:
            # Avisamos que ya la estamos trabajando
            job["status"] = "processing"
            await redis_client.set(key, json.dumps(job))

            # Acá iría el grafo de LangGraph. Lo simulamos con 5 segundos.
            await asyncio.sleep(5)

            job["status"] = "completed"
            job["result"] = f"Resultado procesado para: {job['query']}"
        except Exception as e:
            # Si algo falla, lo dejamos escrito. Sin esto, el cliente se
            # quedaría consultando "processing" para siempre.
            job["status"] = "failed"
            job["result"] = str(e)

        await redis_client.set(key, json.dumps(job))


# Al arrancar la API, lanzamos el worker en segundo plano
# (este bloque ya viene en el código inicial)
@app.on_event("startup")
async def startup_event():
    asyncio.create_task(task_worker())
Supervisar

Human-in-the-Loop: pausar, persistir y reanudar

HITL: el agente se detiene antes de una acción crítica y espera a que una persona la apruebe.

sí: lo que sale caro si sale mal

Un reembolso grande, borrar datos, mandarle un correo a un cliente, ejecutar una herramienta con efectos en el mundo real.

no: todo

Si una persona revisa cada respuesta, se pierde la ventaja de automatizar. HITL no es "manual": es automatización asistida.

NecesitaPara qué
Un punto de pausaDetener la ejecución del grafo en el nodo crítico.
Un checkpointerGuardar el estado del hilo (thread_id) mientras se espera. Pueden pasar minutos u horas: el proceso no puede quedar en memoria esperando. Es la persistencia de la clase 5.

Human-in-the-loop: el agente se detiene y espera la aprobación. Human-on-the-loop: el agente actúa solo, y una persona vigila desde afuera y puede intervenir después.

Ejemplo: un reembolso que necesita aprobación

Código completo · copiá, pegá y corré · sin API keys 
# =====================================================================
# HITL: un grafo que se pausa para pedir aprobación humana
# =====================================================================
# Antes de correrlo (una sola vez):  pip install langgraph
# =====================================================================
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver
from langgraph.types import interrupt, Command

class Estado(TypedDict):
    pedido: str
    monto: float
    aprobado: bool
    resultado: str

def evaluar(estado: Estado) -> dict:
    # Acá iría la lógica normal del agente (clasificar, usar herramientas...)
    return {}

def aprobacion_humana(estado: Estado) -> dict:
    # Regla de negocio: por debajo de 1000 no hace falta un humano
    if estado["monto"] < 1000:
        return {"aprobado": True}

    # interrupt() PAUSA el grafo y guarda el estado en el checkpointer.
    # El diccionario es lo que ve el revisor desde afuera.
    # Cuando alguien reanude, interrupt() devuelve su respuesta.
    decision = interrupt({
        "pregunta": f"¿Aprobás el reembolso de {estado['monto']} USD?",
        "pedido": estado["pedido"],
    })
    return {"aprobado": decision == "si"}

def ejecutar(estado: Estado) -> dict:
    # La acción con efectos (cobrar, reembolsar) va en un nodo POSTERIOR
    # al interrupt, nunca antes dentro del mismo nodo.
    if estado["aprobado"]:
        return {"resultado": "Reembolso ejecutado"}
    return {"resultado": "Reembolso rechazado por el revisor"}

builder = StateGraph(Estado)
builder.add_node("evaluar", evaluar)
builder.add_node("aprobacion_humana", aprobacion_humana)
builder.add_node("ejecutar", ejecutar)
builder.add_edge(START, "evaluar")
builder.add_edge("evaluar", "aprobacion_humana")
builder.add_edge("aprobacion_humana", "ejecutar")
builder.add_edge("ejecutar", END)

# Sin checkpointer no hay pausa posible: no habría dónde guardar el estado
graph = builder.compile(checkpointer=MemorySaver())

if __name__ == "__main__":
    # El thread_id identifica ESTA tarea
    config = {"configurable": {"thread_id": "pedido-42"}}

    graph.invoke({"pedido": "42", "monto": 2500, "aprobado": False, "resultado": ""}, config)
    # .next dice qué nodo quedó pendiente: el grafo está pausado
    print(graph.get_state(config).next)       # ('aprobacion_humana',)

    # ... más tarde, cuando el revisor decide:
    graph.invoke(Command(resume="si"), config)
    print(graph.get_state(config).values["resultado"])   # Reembolso ejecutado

Tres cosas para tener en cuenta

evaluar
→
aprobacion_humanainterrupt() → PAUSA
⏸
revisorCommand(resume="si")
→
ejecutarrecién acá, la acción real
PiezaQué hace
interrupt({...})Detiene el grafo y le pasa al exterior el diccionario con la pregunta. El estado queda guardado en el checkpointer, bajo ese thread_id.
Command(resume=...)Reanuda el mismo hilo. El valor que pasás ("si" o "no") es lo que devuelve interrupt() dentro del nodo.
get_state(config).nextDice qué nodo quedó pendiente. Si no está vacío, el grafo está pausado.
cuidado: al reanudar, el nodo se ejecuta otra vez desde el principio

Por eso no pongas código con efectos antes del interrupt() (cobrar, enviar un correo): se ejecutaría dos veces. Ponelo en el nodo siguiente.

De memoria a Redis, y dos endpoints

MemorySaver sirve para probar, pero se borra si el proceso se reinicia. En producción, el estado vive en Redis: solo cambia el checkpointer.

from langgraph.checkpoint.redis import RedisSaver     # pip install langgraph-checkpoint-redis

with RedisSaver.from_conn_string("redis://localhost:6379") as checkpointer:
    checkpointer.setup()                          # crea los índices la primera vez
    graph = builder.compile(checkpointer=checkpointer)
@app.post("/tasks/{task_id}/start")
def iniciar(task_id: str, monto: float):
    config = {"configurable": {"thread_id": task_id}}    # el task_id ES el thread_id
    graph.invoke({"pedido": task_id, "monto": monto, "aprobado": False, "resultado": ""}, config)
    estado = graph.get_state(config)
    if estado.next:                                      # quedó un nodo pendiente: está pausado
        return {"status": "esperando_aprobacion"}
    return {"status": "completado", "resultado": estado.values["resultado"]}

@app.post("/tasks/{task_id}/approve")
def aprobar(task_id: str, decision: Decision):          # Decision: un BaseModel con aprobado: bool
    config = {"configurable": {"thread_id": task_id}}
    graph.invoke(Command(resume="si" if decision.aprobado else "no"), config)
    return {"status": "completado", "resultado": graph.get_state(config).values["resultado"]}

Como el task_id funciona de thread_id, el endpoint de aprobación reanuda exactamente la tarea que quedó pausada. Dentro de endpoints async, usá AsyncRedisSaver con await graph.ainvoke(...).

Criterios para diseñar la supervisión humana

🎯 Selectiva, no total

Solo se desvían al experto los casos ambiguos o críticos. Revisar el 100% elimina la escala y el ahorro de la IA.

🚦 Dos disparadores

Baja confianza del modelo, o una regla de negocio por riesgo (un monto alto, un tema legal), sin importar qué tan seguro esté el modelo. Se combinan los dos.

💾 Persistencia obligatoria

Sin checkpoints no hay supervisión asíncrona: el sistema tiene que poder esperar horas o días y retomar exactamente donde quedó.

🧹 El feedback se valida

Las correcciones humanas no van directo al reentrenamiento: las personas también se equivocan y tienen sesgos. Primero se validan y se limpian.

Auditoría y compliance: en sectores regulados (finanzas, salud, legal), registrar quién aprobó qué, con qué contexto y por qué es un requisito. HITL deja esa evidencia de supervisión responsable.

Resumen de la clase

  • Los LLM fallan "en silencio": responden 200 OK pero alucinan o tardan de más. Sin trazas, no sabés qué pasó.
  • Traza = el viaje completo; span = cada paso; evals = si el resultado es confiable.
  • Phoenix: abierto, local y agnóstico del framework. LangSmith: integración directa con LangChain y LangGraph.
  • Mirá percentiles (p95), no promedios, y el costo por ejecución.
  • El agente no corre dentro del request: FastAPI encola en Redis y devuelve un Job ID; un worker procesa; el cliente consulta por polling.
  • Registrá el estado antes de encolar, y marcá failed si el worker falla.
  • HITL: interrupt() pausa, el checkpointer guarda, Command(resume=...) reanuda. Solo para lo crítico.

errores a evitar
